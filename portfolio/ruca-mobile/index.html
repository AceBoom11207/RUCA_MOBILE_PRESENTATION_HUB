Independent product project · Native Android · 2026

RUCA OS
Mobile Companion

Carry the desktop’s responsibilities into a handheld experience without shrinking the entire desktop onto a smaller screen.

My contribution
Mobile information architecture, navigation, touch behavior, connection states, and acceptance criteria
Existing foundation
Native Android companion communicating with the Windows desktop over an authenticated local-network bridge
Current direction
Refine the existing application around a touch-first, six-port HOME and five destinations

The design problem

A desktop can expose several information channels at once. A handheld needs a smaller set of useful actions, readable feedback, and a clear relationship to the computer it controls.

The companion is a separate native Android application, not the desktop website in a phone-sized frame. The existing application is the implementation foundation for the current UX work.

Keep the responsibility.
Change the interaction.

Desktop

Simultaneous system awareness, detailed instruments, and controller-style or pointer navigation.

Companion

Touch-first actions, selective information, progressive detail, and visible connection feedback.

The design keeps media, system state, and command responsibilities connected to the same desktop authority. It does not create a second, conflicting version of playback state or telemetry.

A purposeful mobile model

The current design direction gives HOME six user-configurable ports. A tap uses an assigned port; press-and-hold enters configuration. Empty, assigned, pressed, and unavailable states must be distinguishable.

HOMESix configurable ports for the user’s preferred responsibilities.
MEDIAThe desktop session’s playback, volume, and now-playing information.
SYSTEM HEARTThe connected PC’s system condition, not an invented mobile health score.
COMMAND DECKSupported desktop actions with confirmation and clear results.
DIAGNOSTICSImportant telemetry and issues first, with deeper detail when needed.
Design model, not a runtime screenshot

This overview describes the current mobile UX direction. It does not imply that every listed refinement has passed final device validation.

Design for interrupted connections

Connected is not the same as current.

A reachable PC can still supply missing or stale sensor data. The interface must distinguish connection status from the freshness and availability of each reading.

An action needs an outcome.

Pressed, loading, confirmed, unavailable, and failed states need visible feedback. Haptics can reinforce that feedback, but cannot replace it.

A touch target is not a tiny desktop control.

Controls must be readable and usable at handheld distance. Disruptive commands need protection against accidental activation, and state should not depend on color alone.

Existing application vs. refinement

The documented native foundation includes Android-to-Windows communication, media and volume controls, desktop commands, sleep/wake behavior, and device adaptation work. The current UX pass is intended to improve that existing application rather than duplicate it.

The six-port presentation and connection-state refinements are design and implementation work in progress. Multi-host selection remains a research direction, not a shipped claim.

Separate products, clearly named

The public browser link demonstrates desktop RUCA OS. It is not labeled as an Android demo here. This case study covers the native companion’s product direction and existing implementation foundation.

What this work demonstrates

The central design challenge is consistency without identical layouts: preserve the desktop’s information meaning and action ownership while changing hierarchy, navigation, and feedback for touch.

The next validation work is to reconcile the refined flows with the installed application, check missing-data and interrupted-connection behavior, and test whether users understand what computer a command affects.
